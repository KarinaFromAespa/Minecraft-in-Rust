## Method

No driver was run and no code was executed. Every check is `javap -c` on the named 26.1 server-game jar (`~/workspace/mcir-work/26.1.x/versions/26.1/jars/server-game.jar`, Mojang-mapped; client jar from the same directory for render/client-only classes), plus the Rust source in `versions/26.1/crates/` (read-only) and the prepared 26.1 data in `versions/26.1/.local/horizon-client/26.1/`, plus jar-data scans. "Pass" means the static comparison found no divergence; it is not a run result. Oracle statuses are Batch 0's MEASURED table (`docs/sweep/26.1/batch-0-oracles.json`, quoted with pass/fail + error class + error count throughout) — no import-level substitution. Every failing oracle's first error was additionally javap-verified against the 26.1 jar (missing symbol/package/constructor confirmed absent, or cascade dependency confirmed broken).

Vanilla 26.1's own jar/data is the spec throughout (owner's vanilla-check rule). Where the port's behaviour matches the 26.3 base but not 26.1, that is recorded as a defect; where 26.1's vanilla differs from 1.21.7's, the 1.21.7 defect is withdrawn, not carried over. Where 26.1's vanilla differs from 26.2's, the 26.2 verdict is NOT carried over — each such check was re-verified against the 26.1 jar (bed BE, piston `BlockState.CODEC`, pot sherds, sign fields, furnace save format).

**Diff-based carry-over.** Every Batch 4 Rust file was diffed 26.2 → 26.1. Files with 0 changed lines (`storage.rs`, `stations.rs`, `game/trial_spawner.rs`, `vault.rs`, `beacon.rs`, `campfire.rs`, `recipe_book.rs`, `menu_clicks.rs`, `gamerules.rs`, `native_machines.rs`, `redstone.rs`) carry the 26.2 method-2 pass directly where vanilla 26.1 matches 26.2 (spot-verified by javap at each check); files with small diffs were re-verified at each hunk against the 26.1 jar (see "What passed"). The rewritten files (`furnace.rs`, `menu.rs`, `merchant.rs`, `items.rs` fuel table + loot keys, `block_entity_nbt.rs`, `block_entity_item.rs`) were verified in full against 26.1 bytecode, including three programmatic table comparisons (fuel values, brewing mixes, trade-set numbers — the last of which found B4-G25).

## Systemic finding

The 1.21.7 systemic cause — the port carrying 26.x component/tag logic for lookups that do not exist in the target version — is **present again for 26.1, in the opposite direction from 26.2**: the 26.1 port was written largely against 26.3's forms, and 26.1's vanilla differs from 26.3 in more places than 26.2's does. Thirteen of the 22 behaviour defects are 26.3-form leaks into 26.1: the furnace `>=` completion and fuel-remainder drop (G04/G05), the cartography `#extendable_maps` gate (G16, major), the smoker/blast burn-time halving dropped (G17), the dispenser mud tag misspelled (G18), the op-only `setEntityData` merge (G20), the merchant `mayPickup` gate (G21), the exploration-map exclusion dropped (G22), the Hero discount in f32 (G23), the immediate level-up (G24), the merchant float-number reads (G25, major), the loot `modifier`/`condition`-kind keys (G26), the furnace int-times + `speed_multiplier` save format and the sign `allow_op_features` tag (G27), the pot-sherds compound form (G28), and the crafter trigger's plural `recipes` key (G29). Two of the three 1.21.7 majors ARE fixed here (furnaces light from the `FuelValues` table, brewing brews from the `#brewing_fuel` tag) — the fuel table matches `FuelValues.vanillaBurnTimes` entry-for-entry (verified programmatically, including the `#non_flammable_wood` removal) and the 63 potion mixes + 2 container mixes match `PotionBrewing.addVanillaMixes` in set and order — but the third major (cartography) reproduces, and a new major (merchant float numbers: zero offers from every trade set) was found.

Five 1.21.7 defects are withdrawn because **vanilla itself changed between 1.21.7 and 26.1** — the 1.21.7 defect was real there, but the same code is correct against 26.1: furnace `burn()` now grows by the full result count, a lit furnace with no recipe now keeps its timer, spawn eggs lost the `defaultType` fallback, `spawner_blocks_work` now exists and is checked, and creative enchanting no longer requires lapis. The remaining four carry-overs are one-off logic divergences unchanged from 1.21.7 (hopper bowl, crafter eject/trigger, ender-chest LAN scope, decorated-pot container view), plus beds, which reproduce in reduced form (26.1 HAS a bed BE type; 26.2 does not).

Oracle breakage is heavier than 26.2's: only 18 of the 34 in-scope oracles pass (26.2: 16 of 26 in its family, plus its extras). The 16 failures are dominated by 26.3-only APIs the oracles were written against — `EntityTypes` (G4), `net.minecraft.util.Prediction`, `EntitySpawnRequest`, `UvMapping`, `renderpearl`, the 26.3 `ContextMap` API, `datapackWorldRegistries()` — plus the `fuelValues()` abstract-method gap (Batch 0 G1) and three cascades on the broken `VanillaBlockUpdateOracle` (Batch 2's item).

## Behaviour defects

### Major

**B4-G16 — Cartography paper zoom never works: the port gates it on `#extendable_maps`, a tag 26.1 does not have.** `carto_changed` (`horizon-client/src/game/menu.rs:1262`, gate at 1281) requires the map to be in `#minecraft:extendable_maps` before the paper branch runs; the tag is absent from the 26.1 jar data AND the prepared data (0 entries in either). Vanilla 26.1 `CartographyTableMenu` has ZERO `ItemTags` references (javap); its paper branch is `extra.is(PAPER) && !locked && scale < 4`. Every paper zoom in the port is a no-op. Glass-pane lock and map copy (count 2) match vanilla. Carried over from 1.21.7 (same defect, same cause).

**B4-G25 — Villager and wandering-trader trading yields no offers at all: 26.1 trade data writes whole numbers as floats, and the port reads them as ints.** `int_provider` (`horizon-client/src/merchant.rs:675`) uses `serde_json::Number::as_i64()`, which returns `None` for a float — and 26.1's `trade_set` data writes `"amount": 2.0`, `"count": 8.0`, `"max_uses": 3.0`, `"xp": 15.0` (floats throughout the prepared data). Quantified against the prepared data: all **68/68** trade sets have a float `amount` → `offers_from_set` (`merchant.rs:622`) returns zero offers for every set, so no villager or wandering trader ever has anything to sell; every offer-generation path flows through it (`trading.rs` `ensure_offers`, level-up, wandering trader's buying/uncommon/common sets, horizon-ctl `trade`). Even if amount worked: **218/387** trades have a float `wants.count` → the offer is discarded (cost 0 → `return None`); **371/387** have a float `max_uses` → clamped to 1; **266/387** have a float `xp` → 0. Separately, **41/387** trades use the plural `given_item_modifiers` (0 use the singular) but the port reads singular `given_item_modifier` (`merchant.rs:768`) → enchantment modifiers are skipped (enchanted gear sold unenchanted, no price addition). `gives.count` is unaffected (0 float). The 26.2 port fixed the float read with `num_i64`; the 26.1 port kept the 26.3 form. `test_merchant_gate` and `test_merchant_crafted` are both gaps on this defect.

### Minor

**B4-G04 — Furnace completes on `>=` instead of `==`, so a loaded total of 0 finishes in 1 tick.** Vanilla 26.1 `AbstractFurnaceBlockEntity.serverTick` completes only on `==` (`if_icmpne` at bytecode 274); the Rust uses `>=` (`furnace.rs:128`), and its test pins (0,0,1) completing in 1 tick. A furnace loaded with `cooking_total_time` 0 (e.g. from a save that never set it) smelts instantly in the port and stalls in vanilla. The 26.1 port kept the 26.3 form; the 26.2 port fixed it. `test_furnace_loaded_total` is a gap. Carried over from 1.21.7.

**B4-G05 — Fuel remainder is dropped when the fuel stack does not empty.** Vanilla 26.1 `consumeFuel` places the crafting remainder only when the stack empties after the shrink, else it is lost; the Rust drops it when the stack remains (`furnace.rs`, `drops.push`). Only the lava bucket has a remainder in 26.1 data and it stacks to 1, so this is unreachable in vanilla data and reachable only via datapacks. Carried over from 1.21.7.

**B4-G08 — Hopper entity-catch uses the narrow bowl, not the full SUCK_AABB.** `hoppers_catch_items` (`horizon-client/src/game/machines.rs:945`, bowl check 967–974, 0.125..0.875) tests the narrow INSIDE bowl while vanilla 26.1 `HopperBlockEntity.entityInside` intersects the item's box with `getSuckAabb()` (`Hopper` static init: `Block.column(16, 11, 32)` → (0, 11/16, 0)–(1, 2, 1), javap). The tick path covers the full AABB, so pickup can only be 1–2 ticks late for fast items at the edges, never missed. Unchanged from 1.21.7.

**B4-G09 — Crafter never ejects into container ENTITIES** (chest/hopper minecart, chest boat). `crafter_eject` (`horizon-client/src/game/machines/crafter.rs:149`) consults only the block-only `Containers::view`, while vanilla 26.1 `CrafterBlock.dispenseItem` uses `HopperBlockEntity.getContainerAt` (block container first, then the entity container, javap-verified). Hopper and dropper have the entity fallback in the port (`entity_container_at`); the crafter lacks it. The result drops as an item instead. Unchanged from 1.21.7.

**B4-G10 — Crafter `recipe_crafted` trigger fires only for the host player** (LAN-only). The trigger block in `crafter_eject` checks only `self.player` against the 17-box; vanilla 26.1 `CrafterBlock.dispenseItem` iterates ALL `ServerPlayer`s in `AABB.ofSize(center, 17, 17, 17)` (javap). LAN guests in range miss the trigger. (The trigger fires only when a remainder drops — the Rust matches that too.) Unchanged from 1.21.7.

**B4-G13 — No bed block entity: beds load as bare blocks, `/data get block` on a bed returns nothing, port-written saves carry no bed BEs.** Vanilla 26.1 HAS `BedBlockEntity` (`BlockEntityType.BED`, all 16 bed blocks); the port has no Bed variant, `for_block` returns None for beds, and `decode_block_entity` (`save.rs:937`) drops loaded bed BE tags via `BlockEntity::for_block(block)?`. Reduced form vs 1.21.7: 26.1's `BedBlockEntity` has only a `color` field (taken from the block state), no `saveAdditional`, no name — so the 1.21.7 custom-name consequence does NOT apply; the remaining consequences are the missing BE itself (data queries, save round-trip). The port's `block_entity_nbt.rs` knows the `minecraft:bed` id and its save arm writes only the envelope (comment at lines 742–745). (26.2 has no bed BE at all, so this was withdrawn there — 26.1 is the version where it bites.)

**B4-G14 — Ender chest shows the wrong inventory to LAN guests** (LAN-only). `open_ender_chest` (`horizon-client/src/game/storage.rs`) swaps the *host's* `ender_items` into the shared block BE; close copies back and leaves an empty Chest(27). A guest opening the same chest sees the host's items (while the host has it open) or an empty chest — never their own `EnderItems`. Single-player behaviour is correct. Unchanged from 1.21.7 (`storage.rs` has 0 changed lines vs 26.2).

**B4-G15 — Hoppers/droppers cannot see decorated pots, and the port has no pot block entity at all.** `Containers::view` requires a `BlockEntity` in `world.block_entities`; `BlockEntity::for_block` returns `None` for `minecraft:decorated_pot`. Vanilla 26.1 HAS the `minecraft:decorated_pot` block-entity type (`DecoratedPotBlockEntity` implements `ContainerSingleItem$BlockContainerSingleItem` — a 1-slot container — plus `RandomizableContainer`, javap). Hopper insert/extract, dropper insert, and comparator reads of pots all silently fail; `decode_block_entity` drops loaded pot BEs. Manual insert via `use_decorated_pot` works. In `test_pot_hopper`'s scope (still a gap). Unchanged from 1.21.7.

**B4-G17 — Smoker and blast-furnace burn time is not halved: fuel burns twice as long in them.** `Providers::burn_time` ignores `fast` (`providers.rs:111`; its comment wrongly claims "26.1 burn time is the same in every furnace"). Vanilla 26.1 `SmokerBlockEntity`/`BlastFurnaceBlockEntity.getBurnDuration` both return `super.getBurnDuration(...)/2` (javap). The 26.2 port halves; the 26.1 port kept the 26.3 form. (Cooking-time halving is unaffected — it comes from the recipes' own times, 100.)

**B4-G18 — Dispenser water-bottle mud conversion never fires: the port checks the 1.21.7 tag spelling.** The port checks `minecraft:convertible_to_mud` (`dispenser.rs:2249`); 26.1 data has `convertable_to_mud` only (jar data, prepared data, and `BlockTags.CONVERTABLE_TO_MUD` in `DispenseItemBehavior$14`, javap). A dispenser firing a water bottle at dirt never makes mud. (The 26.2 port uses the 26.2 spelling.)

**B4-G19 — Dispenser wax-on sound plays twice.** The wax arm pushes level event 3003, calls `process_level_events()` (which routes 3002..=3005 to `block_particle_event`, playing `item.honeycomb.wax_on` via `play_unshared` for 3003), AND plays the same sound explicitly (`dispenser.rs:2232-2237`). Vanilla 26.1 fires only event 3003 (`DispenseItemBehavior$13`, `HoneycombItem.getWaxed` + `levelEvent(3003)`, javap).

**B4-G20 — An op's spawn egg on a spawner merges entity data; vanilla 26.1 only sets the type.** The port has `set_entity_data` (`mobs/spawner.rs`, called from `creatures.rs:7536-7542` when `acting_player_is_op()`). Vanilla 26.1's `Spawner` interface has NO `setEntityData` (jar-wide byte scan: 0 classes reference it); `SpawnEggItem.useOn` calls only `setEntityId`. Op-only; the 26.2 port removed the merge path.

**B4-G21 — Merchant result take is wrongly gated on `satisfied_by`.** The port's `may_pickup` gates `Role::MerchantResult` on `satisfied_by` (`menu.rs:1503-1513`, the 26.3 form). Vanilla 26.1 `MerchantResultSlot` has NO `mayPickup` override (methods: mayPlace, remove, onQuickCraft, checkTakeAchievements, onTake — javap); `onTake` runs `take(a,b) || take(b,a)` then `overrideXp` unconditionally, with no `onCraftedBy`. A take that vanilla allows (e.g. after the inputs changed) can be refused by the port. The 26.2 port gates on `true`.

**B4-G22 — Exploration maps can be zoomed out via crafting.** The port dropped the exploration predicate (`find_with` without it in `menu.rs` and `machines/crafter.rs`; the `Maps` trait has no `is_exploration_map` in 26.1; `cartography.rs` stores only (locked, scale)). Vanilla 26.1 `MapExtendingRecipe.matches` returns false on `isExplorationMap()` before the scale < 4 check (javap). Zooming an exploration map via the crafting table works in the port and is refused in vanilla.

**B4-G23 — Hero of the Village discount is computed in f32; vanilla uses f64.** The port computes `f64::from(0.3f32 + 0.0625f32 * a)` (`merchant.rs:109`). Vanilla 26.1 `Villager.updateSpecialPrices` uses `0.3d + 0.0625d * amplifier` with `Math.floor` (double, javap — same as 26.2). The results differ only at exact integer boundaries. (The reputation part is float in both — `Mth.floor((float)rep * multiplier)` — and matches.)

**B4-G24 — Villager level-up happens immediately in the trade instead of deferred 40 ticks.** The port levels up at once (`merchant.rs`: `level += 1`, new offers from set, `update_special_prices()`, `Event::LevelUp`). Vanilla 26.1 `Villager.rewardTradeXp` defers: `updateMerchantTimer = 40`, `increaseProfessionLevelOnUpdate = true` (javap — same as 26.2; `increaseMerchantCareer` runs in the villager tick). Entangled: the port resets `special_price_diff = 0` at the start of `update_special_prices` ("from scratch"), while vanilla only ADDS (`addToSpecialPriceDiff`) and resets in `stopTrading` via `resetSpecialPrices()`; `startTrading` calls `updateSpecialPrices` with no reset.

**B4-G26 — Container loot rolls ignore loot functions and misread loot conditions (shared loot engine; Batch 7 overlap).** The 26.1 port's loot engine reads 26.3's key forms: `modifier` (singular) instead of `functions`, and a condition's kind via the `type` key instead of the `condition` key (`horizon-items/src/items.rs`: `modifiers` call sites at 1957–1958/2371 read `["modifier"]` only — zero reads of `"functions"` in the file; `condition()` at 2075 reads `type` only, and an unknown kind falls through to `_ => false`). 26.1's data uses the plural/singular forms throughout: **983** `functions` occurrences across the 1,326 loot tables (0 `modifier`), and **1,545** condition objects naming their kind via the `condition` key. Consequences for containers: chest loot counts are always 1 (`set_count` skipped), enchant/potion/count modifiers never apply, and conditional pools never drop (2 chest files use conditions). The engine is shared with block/mob/fishing loot (Batch 7's scope) — this item records the container-visible impact only; dedup against Batch 7's engine item at merge. (`int_number` handles floats correctly via `as_f64`, so the float `min`/`max` in count providers is NOT part of this defect.)

**B4-G27 — 26.3 save formats leak into the 26.1 canonicalizer: furnace times written as ints + `speed_multiplier`, sign `allow_op_features` kept.** Vanilla 26.1 `AbstractFurnaceBlockEntity.saveAdditional` writes all four times as SHORTS (`putShort`) with no `speed_multiplier`, and `loadAdditional` reads them with `getShortOr` (javap); the port writes ints + `speed_multiplier` 1.0 (`block_entity_nbt.rs:384-388`) — a port-written furnace loses its cooking/lit progress when loaded by vanilla 26.1. (The port's own load reads shorts fine via `number()`, so the loss is one-directional.) Vanilla 26.1 `SignBlockEntity.saveAdditional` writes only `front_text`, `back_text`, `is_waxed` (javap) — no `allow_op_features` (added by datafix 5002, which postdates 26.1); the port's canonicalizer keeps the tag when present (`block_entity_nbt.rs:463-465`). Sign click-command gameplay is unaffected (the port already runs them unconditionally in 26.1, `sign_edit.rs:147`).

**B4-G28 — Decorated-pot sherds are saved in the compound form; vanilla 26.1 uses the list form.** Vanilla 26.1 `PotDecorations.CODEC` is `byNameCodec().sizeLimitedListOf(4).xmap(...)` — a size-limited list of item names (javap, `PotDecorations` static init), and `DecoratedPotBlockEntity.saveAdditional` stores `sherds` through it, only when != EMPTY. The port writes and reads the compound form (`sherds:{back:{id:...},...}`) in both `block_entity_nbt.rs` (canonicalizer) and `block_entity_item.rs` (`pot_decorations` component, pick/place). A port-written pot loses its sherds under vanilla 26.1 (list codec fails → EMPTY), and a vanilla-written pot loses its sherds in the port (the canonicalizer's `Tag::Compound` arm does not match a list → the key is dropped). `test_pot_sherd_templates` and `test_loot_mine_pot_components` are both gaps on this defect. (The 26.2 port uses the list form, measured on real 26.2 Java.)

**B4-G29 — The crafter advancement trigger reads the plural `recipes` key; 26.1 data uses singular `recipe_id`.** `crafter.rs:206` calls `recipe_matches(&c["recipes"], &id)`, and `recipe_matches` returns `true` for a missing key. Vanilla 26.1's `RecipeCraftedTrigger$TriggerInstance.CODEC` uses `recipe_id` (javap), and the only advancement on the trigger (`adventure/crafters_crafting_crafters.json`) has `"recipe_id": "minecraft:crafter"`. Any crafter craft grants "Crafters Crafting Crafters" in the port; vanilla requires crafting a crafter. (The 26.2 port reads the singular key via `adv::recipe_condition`.)

## Suspicions checked and refuted

- Trial-spawner/vault player detection is **not** box-vs-sphere wrong: vanilla `PlayerDetector` uses block-position distance² < range², exactly as the port does.
- Vault key check is **not** item-only: vanilla `isValidToInsert` uses `isSameItemSameComponents`, as the port does.
- Trial-spawner ejection order is **not** wrong: vanilla checks the 30-tick readiness gate *before* the empty-players check, as the port does.
- Merchant takes do **not** award the crafted statistic in vanilla (`MerchantResultSlot.onTake` has no `onCraftedBy`); the port matches.
- The brewing quick-move bottle arm is **not** broken by the missing `#brewing_potion_inputs` tag: `is_bottle` uses the prepared inputs set {potion, splash, lingering, glass bottle}, exactly vanilla 26.1's `PotionSlot` set.
- Anvil rename-cap order matches vanilla bytecode exactly (cap to 39 before the too-expensive check).
- The trial spawner's missing `overridePeacefulAndMobSpawnRule` is **not** a gap: no class in the 26.1 server jar calls the setter, so the field is always false in vanilla gameplay.
- The furnace's missing timer reset on a recipe-less input is **not** a gap in 26.1: vanilla changed (see B4-G06).
- The piston `blockState` bare-name form is **not** a 26.3 leak: 26.1's `BlockState.CODEC` is name-based (javap), unlike 26.2's map form.
- The port's furnace LOAD is **not** broken by the int-times save format: `number()` accepts Short tags, so vanilla saves load correctly; only the save direction loses data (B4-G27).
- The loot engine's float handling is **not** broken: `int_number` routes through `as_f64`, so float `min`/`max` in count providers work — the loot defect (B4-G26) is the key forms only, unlike the merchant float defect (B4-G25).
- The `PotentSulfur` BE variant is dead code, not a defect: `minecraft:potent_sulfur` does not exist in 26.1 data (0 items, no BE type in the jar).
- The sulfur-cube dispenser arm is dead code, not a defect: `#sulfur_cube_swallowable` is absent from 26.1 data and no sulfur items exist.
- Fuel speed is dead code, not a defect: `providers.speed()` always returns 1.0 and vanilla 26.1 has no fuel-speed term.
- `test_craft_map_take` is **not** flipped by the exploration defect: its corpus zooms plain maps only; the exploration exclusion (B4-G22) affects exploration maps alone.
